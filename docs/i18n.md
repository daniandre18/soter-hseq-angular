# Internacionalización (i18n)

La interfaz usa `@jsverse/transloco` con cambio de idioma en runtime. El idioma por defecto y de fallback es español. La preferencia se guarda en `localStorage` bajo `app_language`.

## Arquitectura

- `core/i18n/language.config.ts`: idiomas, locales y clave de persistencia.
- `core/i18n/language.service.ts`: estado con Signals, validación, persistencia y actualización de `<html lang>`.
- `core/i18n/transloco-http.loader.ts`: carga el catálogo global y los scopes desde `public/i18n`.
- `shared/components/language-selector`: selector reutilizable para zonas públicas y autenticadas.
- `shared/pipes/localized-date.pipe.ts` y `localized-currency.pipe.ts`: formato reactivo al locale activo.
- `public/i18n/{es,en}.json`: textos globales.
- `public/i18n/<scope>/{es,en}.json`: catálogos por feature.

Idioma, locale y moneda son independientes. Actualmente `es` usa `es-CO`, `en` usa `en-US`, y las cantidades comerciales siguen expresándose en `COP` salvo que el caso de negocio indique otra moneda.

## Reglas para desarrollar

1. No guardar labels traducidos como IDs ni como valores de dominio. Persistir códigos neutrales como `UNDER_REVIEW`.
2. No agregar nuevos textos de interfaz hardcoded. Usar claves semánticas (`orders.status.underReview`).
3. Dominio, repositorios e infraestructura Firebase no dependen de Transloco.
4. El contenido escrito por usuarios no se traduce.
5. Fechas y números visibles deben usar el locale activo.
6. Los eventos nuevos deberían persistir un código y variables estructuradas; la presentación arma el mensaje traducido.
7. Cada scope debe tener la misma estructura de claves en español e inglés.

Los datos históricos de auditoría y notificaciones que ya contienen frases se mantienen sin migración de Firestore. `shared/utils/domain-labels.ts` conserva compatibilidad al reemplazar códigos conocidos dentro de esos textos; es un adaptador temporal, no el patrón para datos nuevos.

## Agregar portugués

1. Añadir `'pt'` a `AppLanguage`.
2. Agregar `{ code: 'pt', locale: 'pt-BR', translationKey: 'languages.portuguese' }` a `SUPPORTED_LANGUAGES`.
3. Añadir `languages.portuguese` en los catálogos globales.
4. Crear `public/i18n/pt.json` y un `pt.json` dentro de cada scope existente.
5. Ejecutar `npm run lint`, `npm test -- --watch=false` y `npm run build`.

No se necesita cambiar el selector: sus opciones se generan desde `SUPPORTED_LANGUAGES`.

## Cobertura y migración progresiva

La infraestructura global, navegación, autenticación, dashboard, clientes, listado/formulario principal de órdenes, estados/prioridades, cotizaciones, agenda de visitas, detalle de orden (incluida la actividad/composer) y formatos compartidos ya usan i18n. Los modales de clientes, catálogo de servicios, categorías, técnicos y notificaciones conservan algunos textos históricos en español y deben migrarse por scope en iteraciones pequeñas, sin alterar su lógica.

Nota de arquitectura: los `computed()` que llaman `TranslocoService.translate()` directamente (por ejemplo para armar los slices de un chart) deben incluir `languageService.translationsLoaded()` entre sus dependencias leídas. `translate()` es una llamada síncrona sin integración con Signals — sin esa dependencia, el `computed` no se reevalúa cuando el scope todavía no había cargado en el momento del cambio de idioma y el valor queda obsoleto hasta el próximo cambio real de idioma.
